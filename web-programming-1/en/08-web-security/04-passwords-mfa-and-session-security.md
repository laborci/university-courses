# Passwords, MFA and session security

## Goals

By the end of the material, the student understands that logging in is not a single screen, but a process of trust decisions based on each other. You can distinguish password storage from password encryption and hashing, you can tell why a unique, long password and multi-factor authentication are important. It recognizes the role of the session, the main settings of secure cookies, and what risks a protection solution reduces and does not eliminate.

**The password is only one proof of access. The protection of the web account is strong if the service cannot read back the password, if necessary, it asks for additional proof to log in, and the session created after logging in is also carefully protected.**

## The question behind the login

When Anna enters her email address and password into a university system, she ostensibly fills in two fields and presses a button. However, the system must answer several questions. Did Anna really send the request? Does the given secret match what was previously recorded? Do I need a second piece of evidence? If the system accepts the entry, how does the browser note that it is the same person on subsequent requests?

The last question is particularly important because HTTP is fundamentally stateless. A `GET /courses` request by itself does not "remember" who filled out the entry form before it. Therefore, after logging in, the system usually creates a session. The browser receives an ID and sends it on subsequent requests. The server links Anna's logged-in status to this identifier and - together with the authorization management - decides what she can request.

An important thought follows from this: protecting the login form alone is not enough. If someone unauthorizedly obtains the session ID of a browser that is already logged in, they can often pretend to be Anna in the eyes of the system. The password, the second factor, the session and the logout are therefore all part of the same chain of protection.

## The good password: not a memory test

The biggest practical problem with passwords is reuse. If someone uses the same short password on a forum, an old web store, and their university account, a single external data breach can put multiple services at risk. An attacker does not need to crack the most powerful system: it is enough to try an e-mail-password pair obtained from elsewhere on several known sites. This phenomenon is called credential stuffing, mass retrying of credentials.

Therefore, personal good practice is to have a unique, long password for each service. Manually noting this is not a realistic expectation; password management applications take this burden off. They can generate a strong, random password and retrieve it securely. Length is usually worth more than spectacular but predictable character replacement: `Password123!' follows a pattern rather than a true coincidence. A multi-word passphrase used only once or a long string generated by a password manager is a better place to start.

From the service provider's point of view, the password can never be data that is "returned" to the user later. If a site sends the old password via email, it's a sign that the password was stored in a decryptable form - a serious design flaw. Instead, the service generates a one-way check value, a hash, from the password.

## Hash, salt and slow down

A hash function is, simply put, a process that generates a fixed-shaped output from an input. When logging in, the system does not search for the old password, but instead generates the verification value from the entered password and compares it with the stored one. The goal is not to decrypt a secret message, but to determine whether the same secret has been given.Salt is also used for password hashes: this is non-secret additional data that differs from user to user. The salt helps to ensure that two identical passwords do not appear with the same stored value, and that it is not possible to speed up guessing with pre-made tables that work on many accounts. The service may store the salt alongside the hash; its value does not protect it from remaining secret.

Moreover, a fast general hash is not the right tool for a password. The system must choose a deliberately slow method designed for password storage, such as a solution belonging to the Argon2, bcrypt or scrypt family. The slowdown is usually imperceptible to the real user, but it makes a large number of password attempts more expensive. Detailed parameterization is a developer's task; the principle for the listener is that speed is not a virtue here.

An important distinction is that hashing is not the same as encryption. Encrypted data can be decrypted with a suitable key; the purpose of the password hash, on the other hand, is precisely so that the service does not need to know the original password. This adds another risk of a leaked hash database, because weak passwords can be guessed. This is why unique, strong passwords and additional layers of protection are needed.

## Second factor and passkey

Multi-factor authentication (MFA) means that the system asks for more than just one proof. According to the classic division, there can be something that the user knows (password), that he has (hardware security key or authentication application), or that is linked to a physical characteristic (biometrics). Two passwords are not two factors; two different passwords belong to the same category.

A time-based single-use code for the authenticator application is a common solution. The advantage is that it is not just tied to the email account. In several situations, the SMS code is better than password-only login, but it is not considered to be of equal strength: transferring the phone number, the delivery chain and phishing can all be a risk. Therefore, you can request repeated or stronger authentication for operations that are important to the system, such as when changing a password, e-mail address or payment data.

The passkey, i.e. access key, is a modern form of access without a password or instead of a password. The user's device manages a key pair: the secret part remains on the device, the service knows the public part. When logging in, the device provides a proof linked to the given service. The user often approves this by unlocking their device - with a PIN or biometric identification. In this case, the biometrics typically does not travel to the website: it allows the use of the key locally. One of the important advantages of the passkey is that it is tied to the origin, so it cannot be used on the phisher's other domain in the same way as the password.

Neither MFA nor passkey is a magic shield. The user can be deceived, the device can be lost, the recovery process can be weak. Therefore, recovery codes must also be handled securely, and the service must provide transparent notifications and revocation options.

## Session: access card after entry

After a successful login, Anna's browser usually receives a session cookie, for example in the form `session=...`. This value cannot be a verbose, easy-to-guess identifier. The point is not that the cookie is a "secret password" per se, but that whoever owns it can use it to prove their logged-in status until it expires or is revoked. Because of this, the server must use long, random, properly protected identifiers and give the session a limited lifetime.

Some cookie attributes are particularly important. The `Secure' signal asks the browser to send the cookie only over an HTTPS connection. `HttpOnly` means that browser-side JavaScript should not access it directly; this can mitigate the consequences of an XSS bug, but does not resolve the XSS itself. `SameSite` controls when the browser sends the cookie for a request initiated from another site; this is an element of CSRF-type cross-request forgery protection. With the `Path` and `Domain` attributes, the scope of sending can be narrowed.Protection is not the only switch here. The `SameSite` setting, for example, can mitigate, but not replace, thoughtful request protection in all cases. The session must be invalidated when logging out, and a new ID should be issued after a successful login or authorization level change. Thus, there is less chance that a previously recorded identifier will remain usable. The system can monitor for unusual logins and give the user the ability to review active devices and revoke sessions.

## Worked example: entering a study system

Anna opens the HTTPS login page of the university study system. Enter your unique password stored in a password manager. The server searches for Anna's user record, reads out the corresponding salt and the previously formed slow hash, and then compares the corresponding check value of the entered password with this. It does not "reverse" the previous password.

After the password matches, the system asks for a code from an authentication application. Anna approves entry. The server creates a short-lived session, logs access, and returns a `Secure`, `HttpOnly`, appropriate `SameSite` attribute cookie. Anna opens her tickets; the browser automatically sends the cookie to the domain of its own system, and the server identifies the session from this, and then separately checks the authorization of the request.

If someone tries many incorrect passwords to the same account or from one IP address to many accounts, the system may limit the speed of requests (rate limiting), apply a delay, or request additional verification. This is not a punishment, but an increase in the cost of mass trials. At the same time, the permanent, blind account ban can also be used for abuse: someone could exclude Anna on purpose. A good rule seeks a balance between risk and usability.

## Common misconceptions

**"The service must save the password or it won't be able to verify it."** Nope. The server checks the match of the password hash without knowing the original secret.

**"Hash and encryption are the same thing."** Nope. The encryption can be decrypted with the key; the password hash is for verification, not reset.

**"SMS code protects against all attacks."** It may be better than password-only login, but it's not perfect against phishing and phone number-related risks.

**"The HttpOnly cookie completely resolves XSS."** It only restricts whether JavaScript can read the cookie directly. Malfunctioning foreign code can still cause other damage.

**"Logout only changes the state of the screen."** When implemented correctly, it also invalidates the session on the server.

## Glossary

**Password hash:** a one-way check value formed from a password, which is used by the server for comparison.

**Salt (salt):** additional data for password hash formation that differs from user to user.

**MFA:** use of several different types of authentication factors.

**Passkey:** service-related access solution based on a key pair managed on a device.

**Session:** the connection between requests managed by the server, representing the entered status.

**Session cookie:** session identifier sent by the browser for subsequent requests.

**Rate limiting:** limiting the frequency of requests to reduce overload and mass retries.

**CSRF:** is an attack pattern in which another site tries to trick the browser into sending an authenticated request.
